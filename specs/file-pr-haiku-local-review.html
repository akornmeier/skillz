Purpose

Catch actionable defects and coupled-file inconsistencies before the next GitHub upload. Add independent Haiku 5.5 review to /file-pr, keeping review fast, bounded and separate from the model that wrote the changes.

Problem

Current skills/file-pr/SKILL.md checks scope and PR conventions, then creates the PR. It has no explicit local review, repair loop, pre-push checkpoint or freshness receipt. Vendor review happens after upload and can add cost and round trips.

An existing ~/Code/pi-local-review project already explores Durable review, immutable Git snapshots and sandboxed checks. Its README and code explicitly disable live inference; its reviewer is a Gemini simulation with an unrelated provider proposal. Wiring it into this skill today would not produce a real review.

Solution

Use a small foreground TypeScript runner built on the Pi coding-agent SDK. Start two fresh, isolated in-memory sessions against the same immutable Git snapshot. Pin both to Haiku 5.5. One reviews logic, edge cases and failure paths; the other traces callers, schemas, tests, docs and security-sensitive contracts. Both may inspect bounded source at the pinned revisions, but cannot execute commands, edit code, discover skills, call MCP or spawn agents.

Parent agent evaluates each candidate against source, fixes supported defects within the requested scope, runs focused checks, commits only authorized changes, then repeats the full review once if the head changed. Stop on remaining blockers, incomplete coverage or exhausted limits. A clean first round ends immediately. No extra model judges or summary agents by default.

Local orchestration, remote inference. Proposed route is OpenRouter model anthropic/claude-haiku-5.5, verified in its live catalog on 2026-10-21. Catalog canonical slug: anthropic/claude-haiku-5.5-20261007. Canonical metadata is not proof that this dated slug is callable or that an alias cannot change. Recheck availability and record returned model/endpoint; fail on incompatible identity or capabilities. No fuzzy matching, latest alias or fallback to another model. Approve route/privacy before sending code.

Acceptance Criteria

  • Gate. No new branch push or PR creation/update containing new code occurs through /file-pr until review and parent triage cover the current committed candidate. Existing unchanged PR lookup remains free of model calls.
  • Independent. Each snapshot receives two fresh Haiku 5.5 sessions with distinct lenses and no builder conversation. Missing model/auth or a builder already using Haiku 5.5 blocks the independent-model claim and asks for an explicit decision.
  • Evidence. Reports identify exact base/head/merge-base, lens, changed-line evidence and omissions. Parent records supported fixes or evidence-backed dismissals; unsupported model allegations never become automatic edits.
  • Bounded. At most two snapshot rounds per filing attempt, two concurrent lenses per round, three model requests per lens, eight source-tool calls per lens, and a 120-second review deadline per round. No implicit retries, compaction, follow-up agents or background work.
  • Fresh. Receipt verification rejects changed head, intended base, dirty tracked/untracked source, prompt/tool/runtime policy or review settings. Any fix/rebase/new base invalidates the old receipt; second-round work reviews the full PR diff, not only the fix.
  • Readonly. Review sessions can read only filtered text from pinned Git objects through two narrow tools. No checkout scripts, hooks, host-file reads, credential files, GitHub writes or generic shell tools execute on the review path.
  • Rollout. Deterministic fixture tests pass before optional paid calibration. Release evidence records detection, false positives, time, usage and cost without claiming vendor savings or production quality from simulated responses.

Non-goals: replacing GitHub CI or humans; disabling vendor subscriptions; guaranteeing bug absence; reviewing every working-tree edit; installing hooks globally; a daemon, queue, watcher, dashboard or autonomous fixer; changing the existing Durable pilot or any product repository.

Constraints: preserve repository PR conventions, ready-for-review default, model/harness attribution, existing-PR handling and optional babysitting. Fetch is read-only remote access, not a code upload. Rebase latest intended base before the final review, resolving conflicts with user involvement. No push, service, credential change, dependency download or paid call during this planning task.

Open decisions / live blockers: SDK architecture, API-key authentication and $1.02 per-attempt scheduling ceiling are approved. Still require exact OpenRouter upstream/privacy, scoped source export and dedicated key-file access, aggregate calibration cost/request/time budget, paid behavioral matrix and rollout acceptance. The $1.02 ceiling is conservative scheduling headroom, not expected spend or paid-call authorization. Model discovery in the parent harness is not authentication for this standalone transport; live authenticated generation remains unverified.
