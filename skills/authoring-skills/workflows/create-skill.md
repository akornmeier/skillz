# Create Skill

1. Scope: define one capability and its output. Confirm intended client, location, and mutation scope. Use `references/compatibility.md` for portable fields, discovery, and environment setup; a local install convention is not universal.
2. Locate: choose the requested project/user target for that client and confirm no conflicting directory exists. Resolve editing and loaded targets separately; ask when ambiguous. Do not alter another installed copy or symlink without approval.
3. Define evaluations before extensive body expansion: fill `templates/evals.json` with at least three execution cases, realistic fixtures, and observable expected/forbidden behavior. Retain all three repository release profiles. Design separate automatic-discovery positives and negative near-misses; explicit invocation tests execution, not automatic selection.
4. Design baseline: compare a new skill with no skill on identical prompts, fixtures, exact provider/model/thinking, tools, permissions, and containment. Read evaluation guidance in `references/authoring-guidelines.md` when designing this comparison. Plan evidence first; do not launch models without approved budgets and safe preflight. A missing baseline is an unqualified comparison, not invented success.
5. Describe and author: read the guideline sections for the decision at hand and use `templates/SKILL.md`. Explain capability, intent, and boundaries; prefer consistent third-person phrasing without treating it as validity. Keep body instructions imperative. Do not append exact failed queries to win a trigger sample.
6. Add supporting files only where useful: templates for verifiable interfaces, references for needed depth, reusable helpers for deterministic work. Provide clear routing and script interfaces. Accept shared references and sufficient section reads. Put non-obvious gotchas before the decision they govern.
7. Validate: after approved dependency setup, run `uv run --offline --script <base>/scripts/lint_skill.py <new-skill-dir>` under the intended target contract. Repair errors and rerun until exit 0; review advice rather than blindly applying every suggestion. Static checks do not grade task quality.
8. Assess: use `references/review-rubric.md`, recording all fourteen evidence statuses for comprehensive creation. Fix real failures and rerun affected checks. Static files prove neither temporal authorship nor observed behavior. Unassessed behavior keeps release qualification incomplete.
9. Qualify only with approval: follow `references/tuning-diagnostics.md` and, where present, `<repo>/evals/README.md`. Obtain exact profile mappings, cost/time and top-level/nested budgets, isolated discovery, and demonstrated external containment. Validate definitions with `node evals/scripts/validate-cases.mjs` from repository root. Run controlled no-skill/with-skill comparisons across required profiles only inside approved limits; grade every assertion from primary evidence and save schema-conforming records. Missing prerequisites mean blocked cells, not a bypass or successful observation.
10. Report: path, changed artifacts, static metadata/body/scenario estimates, scoped rubric evidence, tests actually run, baseline comparisons if executed, and remaining qualification. No live run means explicit unqualified behavior, not an implicit pass.
